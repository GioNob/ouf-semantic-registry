## Trusted integration contract

The installer provisions exactly one root-private consumption journal per candidate, bound to installation/entity/CID/transaction and immutable intent and broker configuration hashes. Constructor and record validation do not create or repair journals. The source-sealed broker authenticates locally configured producers, independently obtains runc created-state, complete OCI and PID/startTicks/network namespace inode, and publishes CREATED. It accepts final authenticated evidence only for that same OCI and generation, publishes READY and runs the real preparer. It seals the resulting private driver hash once. Source/schema drift, unapproved NICs or authority mismatch fail closed. Broker interfaces are explicit; the shipped CI fixture must not be installed as that broker.

The adapter v3 immutable per-CID entry uses intentRef, bundleParents and broker admissionConfiguration/hash instead of a final approval hash that cannot exist before runtime creation. Per-CID binding excludes other registry entries. Source/runtime/interpreter/broker hashes remain pinned. At admission, it requires driver v4 and a READY consumption receipt matching initial intent/configuration hash, final evidence/approval/driver hash, full OCI and scope/generation. Preparer v2 source closure has fourteen sources; driver v4 has thirteen. Legacy v1/v2/v3 closures are unchanged. The source-only package v4 adds protocol, consumption and its new stager to the fifteen-source v3 closure, eighteen files total.

Consumption transitions:

| State | Required durable fields | Next operation |
| --- | --- | --- |
| STAGED | immutable binding, other fields null | authenticate creation-only intent |
| CREATING | initial binding, other fields null | independently record completed native create |
| CREATED | complete OCI hash and process generation | authenticate attestation and final approval |
| READY | evidence and approval hashes; driver hash sealed once | recheck live guard/lease/authority then claim |
| STARTING | all hashes and generation | single native start attempt; failures require recovery |
| STARTED | all hashes and generation | no second consume/start |

All core mutations use the existing common lock. consume_locked is an internal trusted-driver operation: its caller must already hold that lock, which Preexec.before_process does. The driver verifies current generation through NativeBackend and invokes consumption after its final live bindings and authority checks. Journal compare-and-replace and file/directory fsync precede starter invocation. No cooperating refresh or revocation writer may bypass the same lock. At-most-once is per provisioned journal and cooperating protocol; it does not constrain an actor with root who clones/replaces journals or locks outside the protocol. STARTED means the native start command succeeded, not service/application readiness. No failed state is silently reset or retried, including a crash after native start and before final publication.

Concrete production producer identity, mandate verification, image/rootfs inspection, signer/verification algorithm and bounded authenticator runtime remain integration responsibilities. Initial intent and final approval stay valid only within the 300-second bound, with fresh checks after external authentication and immediately before native start. A root-private hash alone is not issuer authentication. Actual target start requires explicit authorization independently of successful contract/package tests.
